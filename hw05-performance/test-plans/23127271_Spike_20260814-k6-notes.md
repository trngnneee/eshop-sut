# k6 Spike stages vs JMeter Ultimate Thread Group (23127271)

JMeter `23127271_Spike_20260814.jmx` uses **jp@gc Ultimate Thread Group**: 30 s at 5 → jump to 80 in 2 s → hold 60 s → drop to 5 in 5 s → hold 90 s recover. Peak **80** (below Stress **100**). Think Uniform 0–200 ms per sampler.

k6 `23127271_Spike_20260814.js` uses **ramping-vus** with `startVUs: 5` so the first stage is **30 s at 5**, not a 0→5 ramp (a naive `stages: [{duration:'30s', target:5}]` would spend the “baseline” climbing from 0). Remaining stages match the JMeter schedule.

| Window (from k6 t=0) | Target VUs | Purpose |
|----------------------|------------|---------|
| 0–30 s | 5 | baseline |
| 30–32 s | 5→80 | jump |
| 32–92 s | 80 | hold |
| 92–97 s | 80→5 | drop |
| 97–187 s | 5 | recover |

Whole-run `http_req_duration` p95 **mixes** hold + recover (same trap as JMeter Aggregate). K07 must split JSON timestamps. Graded file: `logs/23127271_Spike_20260814.json`.
